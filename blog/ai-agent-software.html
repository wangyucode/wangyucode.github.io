CI/CD 已死？当 AI Agent 开始自己开发、部署和维护软件

2026-10-16Life
AIAgent软件工程

当 AI Agent 从辅助我们写代码，进化到能够自主开发、部署和维护软件时，我们今天熟悉的软件工程体系，还需要吗？

从一个真实的例子说起

写这篇文章的时候，我的 Agent 正在帮我的个人网站干活：合并 GitHub 上几个依赖升级的 PR，重写一篇九年前的老博客，然后构建部署上线。

我做的事：说目标，加约束——"在 dev 分支上改，改完跑 lint，部署前给我确认"。剩下的是它自己完成的：拉代码、装依赖、把 dev server 跑起来、改文章、发现页面渲染有个老 bug、定位到代码、修掉、验证、汇报。全程我没有打开 IDE。

这不是什么前沿实验，就是我现在的日常工作流。我在这套流程里已经跑了几个月：服务器日报是它每天自动生成的，我的几个 AI 项目是它在推进的，出了线上告警也是它先看日志。所以今天聊的话题，不是我对着 PPT 想象未来，而是从一个已经跑起来的工作流往外推：如果 Agent 能持续地开发、测试、部署和维护软件，我们今天这套软件工程体系，还有多少会留下来？

先把答案说在前面：软件工程不会消失，但它的执行主体、抽象层次和人机分工，可能发生根本性的变化。

传统流程是为人类协作设计的

想想我们现在这套东西是为了解决什么问题：

  • Git：多人协作、分支管理、历史追溯；
  • CI/CD：把构建、测试、部署这些重复劳动固化成自动化流水线；
  • Docker：环境隔离和应用分发；
  • GitHub 平台：承载仓库、PR、Code Review 和工作流。

这套体系的前提是：操作软件的人是人类。人有遗忘，所以需要流程规范；人有情绪和立场，所以需要 Code Review；人下班会关电脑，所以自动化要靠预定义的流水线兜底。

而 Agent 不一样：它可以 7×24 在云端运行，可以同时承担开发、审查和测试的角色，可以在软件运行中持续收集日志、异常和用户反馈，然后直接进入下一轮迭代。开发和运维之间那条线，在 Agent 这里是模糊的——它改完代码自己测，测完自己发，发完自己盯。

Git、CI/CD、Docker 会消失吗？

Git：形态会变，需求不会

人类开发者之间的协作，可能不再是 Git 的主要使用场景——Agent 之间的协作未必需要 PR 和 commit message。但版本追溯、差异比较、回滚、审计和责任认定，这些底层需求不会消失。出问题了总要问：改了什么？什么时候改的？谁能回滚？

所以更可能的走向是：从人肉管理分支和合并，转向 Agent 管理软件状态和变更记录，代码历史更多以自动化的变更日志、部署版本和可恢复快照的形式存在。

CI/CD：从流程中心退居为基础能力

传统 CI/CD 是预先定义好的自动化流程——先把"以后要重复做的事"写死，然后一遍遍执行。而 Agent 是根据目标动态决定下一步的：它测试挂了会自己看日志改代码，而不是等你修好流水线。

对个人小项目，Agent 大概率不再需要你维护一套复杂的 CI/CD——它直接就是你的构建、测试和部署。但构建、测试、发布、权限控制、回滚这些能力仍然存在，只是从"你维护的流水线"变成了"Agent 调用的基础设施"。高风险环境（生产数据库、资金操作）仍然需要确定性的流水线作为 Agent 的执行边界。

Docker：用户感知的工具链会消失，解决的问题不会

Agent 可以直接操作服务器完成构建和部署，用户不再需要理解镜像分层和 compose 文件。但隔离、依赖管理、资源限制和可重复部署依然有价值——只是会被进一步封装进 Agent 的执行环境里，你感知不到而已。

大项目和小项目是两回事

上面这些推演，对个人项目和小团队会先发生：Agent 可以拿到较高权限，开发部署全流程高度自动化。但大型企业项目有权限隔离、审批、审计、合规和故障恢复的硬约束，Agent 不该默认拿到生产环境的无限制权限。自动化能力一样重要，只是必须被治理包住。

云端 Agent：24 小时的软件维护员

Agent 真正的威力不在"帮我写代码"，而在持续运行。

想象一个场景：凌晨三点，线上服务异常，监控告警。Agent 收到告警，分析日志，定位问题，在隔离环境里改代码、跑测试、做检查，然后根据预设权限决定是灰度发布还是申请人工审批——发布完继续盯着。天亮你醒来的时候，问题已经修完了，附一份完整的变更记录等你审。

这个场景里没有一步是科幻，每一步都是现有能力的组合。缺的是把它们组织成一个可靠的系统：权限边界、失败恢复、审批策略。

所以软件可能不再是一个"等人来维护的代码仓库"，而是一个由 Agent 持续维护和演进的服务。人类负责定义目标、约束和风险边界，Agent 负责执行。真正有价值的系统，不是无限制授权的 Agent，而是自主性足够、约束同样可靠的 Agent。

AI 原生公司：小公司的结构性优势

传统公司做软件：管理层定目标，项目经理拆任务，开发测试运维分工协作，靠会议、文档和流程系统对齐。

AI 原生公司可能是：人类负责方向、判断和关键决策，一群 Agent 负责执行，云端 Agent 持续推进项目而不是等人触发。管理的重心从"分配任务"变成"定义目标和验收结果"。

为什么说小公司反而有优势？因为它没有历史包袱：没有要兼容的老系统，没有要重塑的审批流程，没有按人头设计的组织架构。它可以从第一天就围绕 Agent 设计工作流，同样的业务，几个人加一堆 Agent 就能跑起来。大公司不是不能转型，但历史系统、数据合规、职责划分、绩效体系，每一条都是惯性。

再看远一点：Agent-to-Agent。用户对自己的 Agent 说"给某人转 500 块"，Agent 找到银行的转账服务，双方通过标准协议交换请求和结果，银行验证身份和权限，执行交易。技术上完全可行，难的是信任问题：怎么确认对面那个 Agent 的身份？授权范围是什么？出了错谁负责？资金操作怎么审计？技术上能实现，不等于商业上可行——这一步需要技术、信任和制度一起演进。

App 会消失吗？

现在的 App 是什么模式：你打开它，在它的固定界面里找功能，学它的操作路径，数据和流程跟别的 App 老死不相往来。

如果 Personal Agent 成为统一入口呢？你说"明天早上八点前到机场，别太贵"，Agent 自己去调地图服务、比价打车、查航班，然后把结果组织成一个适合当前任务的界面给你确认。你不需要知道背后调了哪几个服务——服务能力还在，只是界面不再是预先设计好的 App，而是 Agent 按需生成的。

这会动摇的不只是交互方式：如果流量入口从 App 变成 Agent，传统平台"信息分发"的优势会被削掉一大块。但平台手里的支付、信用、担保、物流和售后处理仍然有价值。未来大概率是直接对接、传统平台和 Agent 平台并存的局面。

下一步的交互：界面是动态生成的

现在的聊天机器人有个根本局限：文字的信息密度太低。你问它牛顿三定律，它给你输出三段定义加公式，你读完还是不会。

更好的方式是：AI 直接生成一个可交互的物理实验场景——你调质量、改力的大小，动画实时展示运动变化，你通过操作去理解公式背后的关系。界面跟着任务走，而不是让你去适应固定的软件结构。

注意这不是"生成一段视频"。视频生成之后是死的，改不了实验条件；可交互场景要求对象、状态、规则和交互逻辑都在，你操作之后它必须给出符合物理规律的响应——这本质上是在构建一个可运行的系统，而不只是渲染一段内容。这也是当前的技术瓶颈所在：生成速度、交互逻辑的正确性、状态一致性、渲染性能。

未来也不一定是所有软件都变成这样——简单问题文字依然最高效，看路线还是地图最合适，做复杂决策图表最直观。更可能的图景是：AI 根据任务，动态组合不同的交互形式。

代码会消失吗？

这是最常被问到的问题。我的判断：代码不会消失，但人类直接面对代码的必要性会下降。

用户表达的会是目标和规则，Agent 维护的会是工作流、经验记忆和自动生成的实现。但代码仍然是必要的：计算机需要明确的执行机制，复杂系统需要可验证的逻辑，高性能和底层系统需要精确控制，安全关键场景需要严格约束。Memory 和自然语言规则替代不了这些。

所以真正值得问的不是"代码会不会消失"，而是**"你是否还需要亲自面对代码"**。对大多数场景，答案会逐渐变成：不需要，但你要能定义清楚要什么，并验证拿到的东西是对的。

对开发者：别把自己定位成写代码的

手写重复代码的价值在下降，熟悉某个框架不再是护城河，机械性的测试、重构、迁移正在被自动化。这已经是正在发生的事，不是预测。

会越来越值钱的能力，我觉得是这些：

  1. 需求澄清和问题拆解——把模糊的业务诉求变成 Agent 能执行的目标和约束；
  2. 架构和边界设计——决定系统怎么分层、Agent 的权限画在哪里；
  3. 验证能力——设计测试、审查结果、判断"Agent 说做完了"是不是真的做完了；
  4. 安全和风险控制——权限最小化、审计、回滚，这些恰恰是 Agent 做不了主的。

我自己的一点体会：不要把自己定位成"写代码的人"，去构建真正能解决问题的 Agent 系统，积累端到端的实践。你在这个过程里踩的坑——权限怎么收、失败怎么恢复、结果怎么验收——才是下一阶段最稀缺的经验。

写在最后

AI Agent 改变的可能不只是编程效率，而是软件的生产方式、交互方式和组织协作方式。工具从我们手里的对象，变成 Agent 调用的基础设施；产品从固定的 App，变成可组合的服务能力和动态生成的界面。

留三个问题给看到这里的你：

  1. 如果今天创办一家软件公司，并且可以充分使用 Agent，你还需要传统的部门、岗位和开发流程吗？
  2. 当用户只需要一个 Personal Agent，未来的软件公司应该向用户提供什么？
  3. 当 Agent 能够开发软件，谁来定义目标、验证结果，并为最终结果负责？

第三个问题，现在还没有好答案。但可以确定的是：越早开始实践的人，越早拿到话语权。
